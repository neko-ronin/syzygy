## 1. Read this first — the correction that shaped the ending

**The orchestrator spent nine rounds applying engineering rigour to an aesthetic
question, and reported the resulting emptiness as progress.**

The night market did not read well. Instead of putting two frames in front of a
vision reviewer and asking "does this look like a place where people shop?", the
thread generated hard numeric targets and chased them: byte values, N·L ratios,
warm/cool separation histograms. Six mechanisms were proposed, all six refuted,
and every refutation was reported as a successful round.

The owner's correction, given at the end of the session, and it is correct:

> Applying hard quantifiable scores toward a goal that is considered subjective,
> on a product that isn't yet remotely presentable let alone MVP, is not an
> acceptable practice.

**Why the rigour was misapplied, in the project's own terms.** `PROCESS.md`
rule 1 says measure rather than guess, and it is right — for **bugs**. A
reverse-Z comparison that renders the world as empty sky is a bug; the byte
value of a market stall at night is a taste question wearing a bug's clothes.
The instrument was right, the question was wrong, and no amount of care in
execution repaired that.

Three compounding errors:

1. **The substitution.** Warm-dominant versus cold-dominant is a *proxy* for
   "does this look like a lit market". Six rounds were spent moving a proxy
   because proxies are measurable and measurable is what the agent could trust.
2. **Refutation read as progress.** Six clean negative results were treated as
   six successful rounds. They were one finding, available in round one: *the
   measurement was not answering the question asked.*
3. **The tell was misread.** Round 18's "finding" — that the sample population
   was mostly non-market floor — was filed as a discovery about the world. It was
   a discovery about the instrument. That is a defect report against six rounds
   of prior work, and it was written up as insight.

**Standing rule adopted at session end:** *for atmosphere and mood, the
instrument is the frame review by a non-implementer vision reviewer against the
reference sheets. Numeric targets for atmosphere are **derived after** a frame is
approved, never invented before one is requested.* This does not weaken rule 1.
It scopes it.

**Expect drift.** The pull toward numbers returns the next time something looks
wrong, and it will look like diligence. `PROCESS.md` rule 8 is the counterweight
and now names this failure explicitly.

## 2. What actually landed

### 2.1 The capture harness was lying — and it was the documented command

**`b2ea352`.** `node tools/capture.mjs --pose=<substr>` **without `--sequence`
never applied the pose.** `opts.poses` is read in exactly one place, inside the
`if (opts.sequence)` branch; a bare `--pose=` fell through to the single-shot
branch, which warmed, settled 45 frames, photographed wherever the free flight
camera was parked, wrote `requested: null`, and printed `PASS`.

```
requested  pos [1.16, 2.6, 0.36]    (eye height, down a market aisle)
held       pos [1058, 444, 337]     (a rooftop, 444 m up)
verdict    PASS
```

`AGENTS.md`, `README.md` and `PROCEDURES.md` all present `--pose=canyon` as
"one shot", and every agent working street-level visuals is told to use it. The
harness's requested-vs-held check — correct, tolerance-tuned, with two paragraphs
of written reasoning — lived one branch away. Cost: two wasted frames and a full
agent round.

The same branch also never called `setTime`/`setWeather`/`setLens`, so even with a
correct camera the *night* pose rendered `dayPhase 0.707`, `sky: clear`,
`exposure 0.92` — the daylight control's values. The sequence branch has applied
`time → weather → lens → pose` since a frame was once mislabelled noon, with the
reason in a comment directly above it. One branch got the lesson; the other was
written before it.

Fixed: the branch resolves the pose, applies that ordering, runs the same
held-camera check with the same tolerances, and prints the agreement next to the
frame (`camera 0.14m from requested`) rather than only on failure. Also: exact
pose names now beat substrings, and a `--pose` matching zero or several poses
fails with the available names.

**Lesson, generalised in `PITFALLS.md` §20:** a guard is only as good as its
coverage, and coverage is not existence. When a check is correct, the next
question is *"which paths reach the frame without passing it?"* Rule 4 had been
added, extended to a second class, written about twice — and still left a whole
code path uncovered, because it was implemented per call site rather than per
capture.

### 2.2 The night market: five mechanisms refuted, one voided measurement

Nine rounds. The record is in `LIGHT_DELIVERY.md` and `ROADMAP.md` R2. The
durable outcome is **not** a fix — it is that the defect is now bounded:

| Hypothesis | Verdict | Decisive measurement |
|---|---|---|
| Lights never reach the buffer | refuted | 933/933 delivered, 0 starved |
| Lanterns hung too high for a stall face | refuted | drop 6.3 m → 3.85 m confirmed baked; flank problem unchanged |
| Stalls sit beside the lanterns | refuted | median 4.92 m, **zero of 27 within 2 m**, at N·L 0.874 |
| Cloth albedo too dark | exonerated | frontage authored **1.7×–9× brighter** than the deck |
| `matAo` dimming vertical faces | exonerated | 0.594 vs 0.798 — and it multiplies the **ambient term only**; the clustered-light term has no `matAo` |
| Widen the lantern radius | refuted (3 held / 3 failed) | deck 4–6 m moved −4.7 → −1.6 but never positive; **the 3 m core rose, which the prediction forbade** |

Then the measurement all of it rested on was voided (`2992cd1`): the "13 known
roadward stall faces" were projected onto **empty aisle**, 2.36 m from the nearest
mesh vertex. Byte 4 with R−B −6.9 was **night sky**; the day frame's luma 119 at
the same pixels was bright facades behind. So the headline "a face receives 12%
of what its geometry predicts" was a lit deck compared against sky.

The replacement histogram (`7a9ae71`, probe validated against a hand-measured
point to 6 px / 4 byte) found frontage **R−B −5.0** against deck **−3.7** — *both
fail identically*, so frontage is not starved relative to the deck.

**Known limit of that instrument, restated rather than buried:** the occlusion
ray covers the market mesh only, not buildings or ground, so a building-occluded
sample counts as visible.

**What is true and worth keeping:** the lantern drop (`d34a47f`, 6.3 m → 3.85 m)
is confirmed baked and correct as far as it goes. Light delivery is plumbing-
sound: `lights == delivered`, 0 starved, on every frame of the presentation set.

### 2.3 Crowd: split in two, and measured

`ab3478b` added **R12 — Living systems** at the owner's direction, because R1's
done-when is a density and a framing and does not require the occupants to do
anything. Five sub-items: gait variety, local avoidance, grouping/flow, city
interaction, traffic-as-agents.

Gate 5 measured two isolated silhouettes at **22×9 and 23×11 px with 20 clear
pixel columns** — those clear the 20–24 px separation target. Packed rows merge
into counter-like bands. So there are **two open causes**, mesh proportions in
`citymesh.ts` and placement/locomotion in `crowd.ts`, and the reviewer was
explicit that "rebuilding alone will not resolve overlapping placement."

dev2 (`eafc69b`) established the standing numbers: **`viewRadius` is the seeding
limit; the ≥40 px gap bin is empty** (`src/sim/__selftest_density.ts`, re-runnable
headlessly). It also nearly lost that bin while tidying code, and the tidied
version "confidently reported the opposite conclusion". Nothing caught that
except a value disagreeing with one recorded an hour earlier — which is the
strongest argument in this file for writing measurements down.
