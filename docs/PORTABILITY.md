# Portability assessment

**Verdict: a three.js port is possible, but is not worth doing on current evidence.** The reusable city data is already separate from GPU upload. The costly part is preserving this renderer's picture and the evidence used to judge it: its deferred passes, procedural materials, light lists, post chain and capture diagnostics. A library replacement has no demonstrated quality or performance benefit in this assessment. That is a cost judgement, not a claim that three.js cannot render the city. The source basis is the CPU mesh contract, the live frame sequence and the automation surface. [geometry.ts:13–24](../src/world/geometry.ts#L13), [renderer.ts:1237–1255](../src/render/renderer.ts#L1237), [main.ts:814–827](../src/main.ts#L814).

This answers **R13's portability section only**. It contains findings and conditional cost descriptions, no work items, migration plan or framework choice. The scope is explicit in [ROADMAP.md:747–750](ROADMAP.md#L747) and [ROADMAP.md:790–803](ROADMAP.md#L790). Repository evidence was read during this round, with `f3a58468d778467e0feed241b8f273c86bce9bb9` as the inspected HEAD. Other engineers were working concurrently; the citations name the source read, not a tested port. No application, browser, capture, build or benchmark was run. External API facts come from the linked official three.js documentation consulted during this assessment. Costs below are **inferences from the named responsibilities**, not calendar estimates or measured speed comparisons.

## What “port to three.js” means here

The owner's decision remains closed: “we're shelving webgl 2. we're going all in on webGPU.” Visitors without WebGPU receive no city. Portability to three.js or WebGL remains wanted, separately from maintaining a second backend. [DECISIONS.md:16–24](DECISIONS.md#L16), [DECISIONS.md:53–62](DECISIONS.md#L53), [gpu.ts:73–78](../src/core/gpu.ts#L73).

These are different costs:

| Interpretation | What it buys and what it costs |
| --- | --- |
| **three.js with WebGPU** | Library ownership of rendering resources and scene submission. It retains the graphics API's capabilities, but adoption replaces the project's raw pipeline/material interfaces. The existing interfaces take GPU layouts, entry points and attachment descriptions directly. [gpuutil.ts:69–118](../src/render/gpuutil.ts#L69). Official three.js uses node materials/TSL for custom WebGPU materials; it does not accept the older `ShaderMaterial`, `RawShaderMaterial` or `onBeforeCompile` routes. [Official migration guide](https://threejs.org/manual/pages/webgpurenderer). **Cost inference:** substantial renderer and application integration, even with WebGPU retained. |
| **three.js with WebGL reach** | A different backend capability contract as well as the library integration. three.js documents automatic WebGL fallback, but its atomic shader nodes are WebGPU-only. This city's binner writes atomic storage that its lighting pass subsequently reads. [lightbin.wgsl:19–26](../src/shaders/lightbin.wgsl#L19), [lightbin.wgsl:85–87](../src/shaders/lightbin.wgsl#L85), [lighting.wgsl:54–61](../src/shaders/lighting.wgsl#L54). [Official renderer options](https://threejs.org/docs/pages/WebGPURenderer.html), [official atomic-node restriction](https://threejs.org/docs/pages/AtomicFunctionNode.html). **Cost inference:** an additional representation/algorithm change for local lighting; automatic fallback does not make the current binner portable. This is the reach trade already shelved under D1, not approval to reopen it. [DECISIONS.md:43–62](DECISIONS.md#L43). |
| **three.js alongside the raw renderer** | The raw frame still owns its encoder, passes and queue submission. [renderer.ts:1248–1255](../src/render/renderer.ts#L1248). **Cost inference:** retaining those responsibilities preserves their coupling; adding a library beside them is not evidence that the renderer has been ported or that its maintenance cost has fallen. |

Runtime dependency policy is also part of the cost. This project deliberately has no runtime npm dependencies; its package declares only development dependencies and does not pin three.js. Library adoption would change that contract as well as rendering code. [DECISIONS.md:223–233](DECISIONS.md#L223), [package.json:15–20](../package.json#L15). No library version or integration prototype exists in the evidence used here, so API availability does not establish visual equivalence or performance.

## The boundary that already exists

The useful boundary is **generated city and baked CPU data → upload and render ownership**. This is an assessment of the existing boundary, not a proposed abstraction. `CityChunk` contains buildings, props, bridges, cables and bounds. The CPU `City` cache constructs and evicts those records. `Mesh` contains typed component arrays and indices; interleaving and GPU allocation happen later in `uploadMesh`. [citygen.ts:79–90](../src/world/citygen.ts#L79), [citygen.ts:1023–1049](../src/world/citygen.ts#L1023), [geometry.ts:2–24](../src/world/geometry.ts#L2), [gpuutil.ts:145–197](../src/render/gpuutil.ts#L145).

**Cost inference:** city generation and mesh baking can remain CPU responsibilities. Their arrays are a natural fit for three.js geometry attributes and indices; that does not make their materials interchangeable. The fourth colour component here is an emissive mask, and instance parameters carry material identity, roughness, emissive strength and seed. Those semantics are consumed by custom shader code. [geometry.ts:5–18](../src/world/geometry.ts#L5), [citymesh.ts:57–100](../src/render/citymesh.ts#L57), [gbuffer.wgsl:10–23](../src/shaders/gbuffer.wgsl#L10). [Official BufferGeometry contract](https://threejs.org/docs/pages/BufferGeometry.html), [official instanced geometry contract](https://threejs.org/docs/pages/InstancedBufferGeometry.html).

The separation is incomplete at the application edge. `main.ts` packs pedestrian and vehicle instances together, passes a callback into the G-buffer pass, binds exposed raw vertex/index buffers and issues indexed draws itself. It then adds entity triangle accounting separately. Crowd output also imports the rendering material IDs and instance stride. [main.ts:438–462](../src/main.ts#L438), [main.ts:492–507](../src/main.ts#L492), [renderer.ts:1421–1443](../src/render/renderer.ts#L1421), [crowd.ts:18–22](../src/sim/crowd.ts#L18). **Cost inference:** a renderer replacement extends into the application draw loop and the instance-output contract; it is not confined to `src/render/`.

## ABI: cross-reference, inventory and a necessary qualification

[ABI_AUDIT.md:27–149](ABI_AUDIT.md#L27) is the existing layout audit. Its stated method is static source reading, with a limit on what that establishes. [ABI_AUDIT.md:14–25](ABI_AUDIT.md#L14). This assessment does not repeat its full offset audit or adopt its proposed work. It inventories the live contracts relevant to a port and checks their current allocation/stride declarations. `FRAME_UNIFORM_SIZE` governs the **Frame binding and upload span**, not every shader buffer. The underlying `GPUContext` allocation is larger. [gpuutil.ts:18–39](../src/render/gpuutil.ts#L18), [gpu.ts:142–146](../src/core/gpu.ts#L142), [renderer.ts:895](../src/render/renderer.ts#L895).

| Live host/shader contract | Current size/stride check and consumer | Meaning for library interop — inference |
| --- | --- | --- |
| **Frame uniform** | WGSL declares nine matrices and nineteen vectors: 880 bytes within the 1024-byte binding span; the device buffer is 64 KiB. The vector writer starts at float 144. **Capacity fits; matrix member agreement is qualified below.** [common.wgsl:7–42](../src/shaders/common.wgsl#L7), [gpuutil.ts:14–39](../src/render/gpuutil.ts#L14), [gpu.ts:142–146](../src/core/gpu.ts#L142), [renderer.ts:844–895](../src/render/renderer.ts#L844). | Semantic fields and matrix conventions remain; a library-generated uniform layout does not promise the same byte offsets. Passing the raw block instead retains this ABI unchanged. |
| **Light storage** | The host writes eight floats per light, matching the two-vector 32-byte declarations in both compute and lighting. [renderer.ts:56–60](../src/render/renderer.ts#L56), [renderer.ts:1186–1202](../src/render/renderer.ts#L1186), [lightbin.wgsl:10–13](../src/shaders/lightbin.wgsl#L10), [lighting.wgsl:24–27](../src/shaders/lighting.wgsl#L24). | Radius/intensity semantics, active count, array representation and both consumers remain a shared contract. These are not the draw-instance records. |
| **Bin storage** | TS allocates 400 bytes per bin; compute writes atomic indices/count and lighting reads the matching non-atomic layout. **TS allocates this record; it does not write its light indices.** [renderer.ts:1561–1577](../src/render/renderer.ts#L1561), [lightbin.wgsl:19–26](../src/shaders/lightbin.wgsl#L19), [lightbin.wgsl:40–87](../src/shaders/lightbin.wgsl#L40), [lighting.wgsl:54–61](../src/shaders/lighting.wgsl#L54). | Producer/consumer layout and access modes remain coupled even if a library allocates storage. The WGSL declarations are duplicated, not imported from one shared struct; module assembly does not include `lightbin` in `lighting`. [wgsl.ts:22–28](../src/render/wgsl.ts#L22). |
| **ShadowParams uniform** | The shader's matrix and two vectors occupy 96 bytes; the host writes each cascade into a 256-byte dynamic slot and binds that slot with a dynamic offset. This has its own allocation, independent of `FRAME_UNIFORM_SIZE`. [shadow.wgsl:11–17](../src/shaders/shadow.wgsl#L11), [renderer.ts:53](../src/render/renderer.ts#L53), [renderer.ts:501–504](../src/render/renderer.ts#L501), [renderer.ts:913–924](../src/render/renderer.ts#L913), [renderer.ts:1397–1414](../src/render/renderer.ts#L1397). | Cascade data, depth/bias meaning and per-pass selection remain; library uniforms replace the raw grouping/alignment contract only if raw-buffer use also ends. |
| **Mesh vertex record / VSIn** | Upload interleaves position, normal, UV, RGB and a separate emissive float into 48 bytes at locations 0–4. Both G-buffer and shadow inputs declare those fields. This is an attribute ABI, not a padded storage struct, and is additional to the instance row in the existing audit. [gpuutil.ts:154–178](../src/render/gpuutil.ts#L154), [gpuutil.ts:199–211](../src/render/gpuutil.ts#L199), [gbuffer.wgsl:10–15](../src/shaders/gbuffer.wgsl#L10), [shadow.wgsl:19–24](../src/shaders/shadow.wgsl#L19). | Arrays are reusable; attribute names/interpretation replace shader locations. Treating the emissive component as ordinary colour alpha would change material meaning. [geometry.ts:5–18](../src/world/geometry.ts#L5). |
| **Instance vertex record / VSIn** | The CPU writer's model, tint and params occupy 24 floats/96 bytes. GPU attributes at locations 5–10 match that record in G-buffer and shadow. [citymesh.ts:57–100](../src/render/citymesh.ts#L57), [gpuutil.ts:213–227](../src/render/gpuutil.ts#L213), [gbuffer.wgsl:17–23](../src/shaders/gbuffer.wgsl#L17), [shadow.wgsl:25–30](../src/shaders/shadow.wgsl#L25). | Library instancing retains transform/appearance meaning through a different attribute/update contract. The application's packed pedestrian/vehicle offsets are part of that contract too. [main.ts:438–452](../src/main.ts#L438). |

`TileLight` is declared but not bound; the live storage bindings are `Light` and `Bin`. Shader-local `Facade`, `Ground`, varyings and fragment outputs are not TS-written buffer structs. [lightbin.wgsl:10–26](../src/shaders/lightbin.wgsl#L10), [gbuffer.wgsl:26–37](../src/shaders/gbuffer.wgsl#L26), [gbuffer.wgsl:97–103](../src/shaders/gbuffer.wgsl#L97), [gbuffer.wgsl:276–282](../src/shaders/gbuffer.wgsl#L276), [gbuffer.wgsl:589–593](../src/shaders/gbuffer.wgsl#L589), [post.wgsl:27–38](../src/shaders/post.wgsl#L27).

**Qualification of the audit's Frame verdict:** the audit describes nine matrix writes and matching member order. The current writer contains eight matrix writes, ending at float 112, then starts vectors at float 144. WGSL has an extra `sunViewProj` before `shadow0` through `shadow3`. Consequently the writer places cascade zero in `sunViewProj`, the next cascades in `shadow0` through `shadow2`, and leaves the declared `shadow3` slot untouched in the zero-initialised frame array. The shader's shadow selector reads `shadow0` through `shadow3`, so this is a member-mapping discrepancy, not insufficient `FRAME_UNIFORM_SIZE`. [ABI_AUDIT.md:51–69](ABI_AUDIT.md#L51), [renderer.ts:280](../src/render/renderer.ts#L280), [renderer.ts:844–857](../src/render/renderer.ts#L844), [common.wgsl:8–18](../src/shaders/common.wgsl#L8), [common.wgsl:294–310](../src/shaders/common.wgsl#L294). No rendering effect was tested here. The audit's unqualified “SAFE” cannot be carried into a port as proof of matrix member agreement. This is a recorded finding, with no fix attached.

Two semantic contracts also outlive byte-layout changes: `grade.w` carries the active light count despite its shader comment, and `time.w` carries the host's render-scale-derived detail flag. [renderer.ts:871–880](../src/render/renderer.ts#L871), [common.wgsl:30–34](../src/shaders/common.wgsl#L30), [lightbin.wgsl:70–75](../src/shaders/lightbin.wgsl#L70), [gbuffer.wgsl:608](../src/shaders/gbuffer.wgsl#L608). **Cost inference:** generated library bindings can remove handwritten offsets, but cannot establish that the host and shader mean the same thing. The interop contract includes semantic values, not only struct size.

The executable server path always launches **Vite dev**, regardless of the stale preview branch/header. ## Assessment boundary and reflection

**The architecture offers reusable CPU data, not a ready-made renderer adapter.** The present cost is a renderer/material/evidence integration effort, with additional local-light implementation cost for WebGL reach. Its extent follows from the GPU ownership and raw draw loop, the shader contract and the harness readback surface cited above. [gpuutil.ts:145–227](../src/render/gpuutil.ts#L145), [renderer.ts:593–690](../src/render/renderer.ts#L593), [main.ts:438–507](../src/main.ts#L438), [main.ts:814–827](../src/main.ts#L814). On that evidence, a port is not justified now. D1's accepted reach limit and the deliberate raw-renderer/dependency policy remain the relevant owner decisions. [DECISIONS.md:43–62](DECISIONS.md#L43), [DECISIONS.md:223–233](DECISIONS.md#L223).

This is still the dispatched audit: the coupling and cost are written down, including a source discrepancy that limits reuse of the existing ABI conclusion. It is characterisation required by the portability row, not implementation or visual approval. No conclusion here establishes three.js frame quality, throughput, memory use, capture reliability or an elapsed migration cost. The other R13 sections and the city's open frame gates are not closed by this document. [ROADMAP.md:768–803](ROADMAP.md#L768).
